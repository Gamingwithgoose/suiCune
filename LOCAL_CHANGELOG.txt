Architecture inventory
----------------------

Startup and main loop
~~~~~~~~~~~~~~~~~~~~~
- The process entry point is `main` in `tools/emu/peanut_sdl.c`.
- Startup initializes PhysFS, SDL video/controller/audio, Game Boy state,
  cartridge RAM, RTC, constant/map/script lookup tables, JSON-backed tables,
  configurable input, the emulated APU, the emulated LCD callback, SDL renderer
  and texture, native sockets, and the emulated Mobile Adapter.
- `USE_ROM_FILE` is currently hardcoded to 0. The normal build does not require
  an external Game Boy ROM file, but it still initializes a `struct gb_s`
  cartridge/CPU/memory model with hardcoded Crystal cartridge metadata.
- Reset paths use `setjmp`/`longjmp`, set emulated CPU PC/SP values, and call
  translated initialization functions.
- The outer application loop is native C: while SDL has not requested quit, it
  calls `Intro_Jumptable()`. `gb_run_frame()` is present but commented out in
  this path. Frame progress ultimately reaches `gb_finish_frame()` and
  `sdl_loop()` through translated game functions such as `DelayFrame()`.
- The loop is therefore a hybrid: SDL owns the host loop and pacing, while
  translated game flow remains coupled to Game Boy CPU registers, addresses,
  hardware registers, and frame/LCD semantics.

Function dispatch and ROM-address identity
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- `functions.c` initializes `redirectFunc[ROM_SIZE]` and
  `convertedFunc[ROM_SIZE]`, indexed by addresses in a 2 MiB ROM-shaped space.
  The audit counted 525 active `CONVERTED(...)`/`REDIRECTED(...)` table entries.
- `funcmap.h`, `global.h`, and the dispatch tables preserve fixed Game Boy ROM
  addresses as runtime identities. Numerous converted macros and functions
  still read/write `gb.cpu_reg`, invoke `gb_read`/`gb_write`, and emulate stack
  and flag behavior.
- The CPU interpreter and opcode machinery remain compiled and callable even
  though the normal outer loop does not call `gb_run_frame()` directly.
- No external ROM is authoritative in the default build, but ROM banking,
  banked addresses, CPU registers, and address-indexed redirection remain
  authoritative runtime concepts. This is not a completed native ROM/data
  conversion.

Memory model
~~~~~~~~~~~~
- `struct gb_s gb` owns emulated WRAM, VRAM, HRAM/OAM/register state, cartridge
  RAM, RTC registers, CPU registers, MBC state, and LCD state.
- `wram` and `vram` are struct views mapped over arrays inside `gb`; HRAM is
  represented by a generated global structure. `global.h` is a generated map of
  original RAM/ROM addresses.
- `gb_read` and `gb_write` remain the central address decoder for ROM banking,
  VRAM banks, cartridge RAM/RTC, WRAM/echo RAM, OAM, HRAM, joypad, timers,
  interrupts, LCD registers, DMA, CGB palettes, audio registers, and WRAM-bank
  selection.
- Audit counts demonstrate the breadth of the dependency: `wram->` occurs
  17,959 times across 315 C/header files; `hram.` occurs 2,902 times across 214
  files; `gb_read(` occurs 634 times across 83 files; `gb_write(` occurs 708
  times across 79 files; `gb.cpu_reg` occurs 934 times across 6 files.
- Some logical state has already moved into C structures, notably global
  `PlayerData gPlayer` and `PokemonData gPokemon`, but their layouts and many
  fields still mirror WRAM/SRAM organization and fixed hardware-era limits.

Rendering
~~~~~~~~~
- Gameplay code loads converted PNG/1bpp/2bpp assets into emulated VRAM and
  constructs tilemaps, palettes, and OAM-compatible sprite data.
- The LCD renderer in `tools/emu/peanut_sdl.c` rasterizes every 160-pixel
  scanline from emulated VRAM, BG/window tile maps, CGB palette registers, LCDC
  state, and OAM using Game Boy priority and addressing rules.
- `lcd_draw_line` converts indexed LCD output into a 160x144 RGB555 framebuffer.
  SDL uploads that framebuffer to one streaming texture and presents it.
- Native SDL is therefore the presentation backend, not an authoritative native
  world/UI/entity renderer. OAM limits, tile addressing, VRAM banks, scanlines,
  and Game Boy LCD registers remain authoritative.

Audio
~~~~~
- Music/SFX data is loaded from native asset files into buffers, and much of the
  music parser is translated C operating on channel structs.
- The translated engine still writes Game Boy NR10-NR52 and wave RAM addresses
  through `gb_write` and reads them through `gb_read`.
- Those addresses are routed to `tools/emu/minigb_apu`, whose stated and actual
  purpose is emulation of the four-channel Game Boy APU. Its SDL callback
  produces host PCM audio.
- SDL audio output is native, but Game Boy APU registers and an emulated APU
  remain the authoritative sound generator. Native audio conversion is not
  complete.

Input
~~~~~
- `util/input.c` is a useful native front end: it maps SDL keyboard/controller
  events to semantic A/B/Start/Select/directional actions and supports a JSON
  binding file.
- The result is packed into the Game Boy joypad bitfield. `home/joypad.c` then
  emulates JOYP register selection/inversion and copies results into HRAM/WRAM
  joypad fields, including legacy auto-input behavior.
- Device acquisition/remapping is native; gameplay input consumption is still
  coupled to Game Boy joypad-register and HRAM semantics.

Save system and serialization
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- The host save path is `read_cart_ram_file`/`write_cart_ram_file` in
  `tools/emu/peanut_sdl.c`.
- Save size is hardcoded to Crystal's 0x8000-byte cartridge RAM size. Two raw
  images (`baserom.sav` and `baserom.sav2`) are allocated and written.
- `OpenSRAM`/`CloseSRAM` still operate by writing MBC3 enable, latch, and bank
  registers. Many gameplay systems directly access banked SRAM addresses.
- `util/serialize.c` explicitly serializes/deserializes selected runtime C
  structures to the original SRAM byte layout. This is better than raw native
  struct serialization and supports unaligned-host safety, but Crystal SRAM
  layout remains the persistent authoritative format.
- The serializer covers player, Pokemon, current-map, options, boxes, objects,
  and related records. Its tests verify byte-for-byte agreement with SRAM, not a
  versioned native save format.
- No native save version, schema migration layer, or format-independent native
  persistence was found.

RTC
~~~
- `util/rtc.c` uses libc `time()`/`localtime()` and records a host timestamp, so
  host clock acquisition is already partly native.
- Host time is converted back into `gb.cart_rtc` MBC3 register fields, and the
  adventure start timestamp is stored in spare bytes inside Crystal-compatible
  player SRAM data.
- `home/time.c` and `engine/rtc/rtc.c` continue to latch/select/read/write MBC3
  RTC registers through `gb_read`/`gb_write` and use HRAM clock fields.
- The RTC is therefore a native time source feeding a legacy emulated RTC and
  save layout, not a completed native RTC subsystem.

Content and asset lookup
~~~~~~~~~~~~~~~~~~~~~~~~
- PhysFS/native file loading is used for graphics, audio binaries, JSON data,
  and optional asset archives. `data/json_load.c` loads several content tables,
  including base stats and wild encounters, into C allocations.
- Many other content tables and assets are compiled as C arrays and direct C
  pointers. This is meaningful progress away from a literal ROM file.
- At the same time, fixed ROM addresses, bank/address macros, GB pointer
  conversion (`GBToRAMAddr`, `gb_pointer`, `MBANK`), generated address maps, and
  ROM-address dispatch tables remain widely used.
- Core expandable IDs remain byte-sized in `constants/types.h`:
  `species_t`, `dex_t`, `item_t`, and `move_t` are all `uint8_t`.
- The runtime is consequently hybrid: native asset files/C tables coexist with
  Game Boy address identity and byte-width content ceilings.

Scripting
~~~~~~~~~
- A native C script state object (`struct Script`) holds a C function pointer,
  position, arguments, and a fixed call stack. Map/event scripts are largely
  expressed as C state-machine functions using scripting macros.
- `ScriptEvents()` dispatches the current C function; the old byte-command
  `RunScriptCommand()` switch is present primarily as commented translated
  reference rather than the active general path.
- Save compatibility still preserves original GB script pointers for map
  objects. `data/script_pointers.c` builds a hash mapping map/index keys and GB
  pointer values to native C script pointers because original Crystal stores
  event script pointers in save data.
- Scripting has substantial native-C structure, but script identity and saved
  map-object data are still restricted by GB pointer/save compatibility.

Maps and overworld objects
~~~~~~~~~~~~~~~~~~~~~~~~~~
- Map headers, attributes, events, connections, blocks, and scripts are compiled
  as C structures and direct pointers. `MapGroupPointers` selects map groups,
  and map setup uses C function-pointer command tables.
- The overworld loop is a C state machine (`OverworldLoop`, `EnterMap`,
  `HandleMap`) that runs map setup, object updates, background work, and script
  events.
- Map group/number fields remain byte-sized and some serialized fields retain GB
  addresses. Connection calculations still target WRAM-backed overworld block
  buffers.
- Entity authority is still the fixed Crystal arrays: `NUM_OBJECT_STRUCTS` is 13
  and `NUM_OBJECTS` is 16. `FindFirstEmptyObjectStruct`, object visibility,
  movement, rendering, collision, and serialization all operate on those fixed
  slots in `gPlayer`.
- This is not yet a dynamic native entity system and cannot satisfy future MMO
  entity requirements without replacement.

Networking, link, and mobile
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- `util/network.c` contains native socket/SDL_net transport and initializes
  UDP/TCP endpoints. This is genuine host networking infrastructure.
- The transport is installed into `gb.gb_serial_tx`/`gb.gb_serial_rx`, and the
  gameplay link code retains Crystal serial/link synchronization, byte exchange,
  time-capsule, trade, and link-room semantics.
- The mobile path uses `libmobile` to emulate a Game Boy Mobile Adapter and its
  serial behavior, while using host sockets underneath.
- Native sockets exist, but the authoritative game protocol is still Game Boy
  serial/Mobile Adapter architecture. This is not an MMO protocol or a native
  remote-player/entity system.

Architectural changes made
--------------------------
- Added native semantic foundations: 16-bit `SpeciesId`, `DexId`, `MoveId`,
  `ItemId`, `FormId`, `AbilityId`, `SpriteId`, `TrainerClassId`, and `TrainerId`;
  8-bit `NatureId` and `TypeId`; 32-bit `PersonalityValue` and `NetPlayerId`.
- Kept `species_t`, `dex_t`, `move_t`, and `item_t` as explicitly documented
  byte-oriented compatibility aliases. Globally widening them was rejected
  because legacy arrays would then be traversed with incorrect 16-bit strides.
- Native wild/fishing/trainer/evolution/learnset/NPC-trade/item tables now carry
  semantic IDs. Native player bag entries separate `ItemId` from 8-bit quantity
  instead of storing both in an alternating item-typed array; aligned anonymous
  pocket blocks preserve the existing generic pocket-access API safely.
- Pokédex bit indexing now accepts `DexId`; the backing array still scales from
  `NUM_POKEMON` and remains part of the current Crystal-compatible save model.
- Crystal SRAM/mobile/Mystery Gift records have explicit legacy byte types.
  Native serializer fields narrow only after a range check; unsupported expanded
  values fail instead of being silently corrupted.

Obsolete Game Boy/emulation dependency removed
-----------------------------------------------
- Removed the byte-width content-ID constraint from confirmed native content
  tables, content-name lookup APIs, player bag entries, and Pokédex flag indices.
- Removed the alternating `[item, quantity, item, quantity]` typed-array model
  from native player bag storage.
- Game Boy byte limits remain authoritative in live `BoxMon`, `PartyMon`,
  `BattleMon`, WRAM battle fields, Crystal save/link/mobile records, and several
  script interfaces. Those dependencies were made explicit, not claimed removed.

Temporary migration code introduced
------------------------------------
- The old lowercase aliases remain byte-sized compatibility types. Removal
  condition: delete each alias only after all callers in its live party/battle,
  WRAM, script, link, and save-format domain have migrated to either a semantic
  native ID or an explicit `Legacy*Id`.
- Checked native-to-legacy conversions remain at trainer, encounter, evolution,
  NPC-trade, registered-item, and serializer boundaries. Removal condition:
  remove a conversion only when its destination is no longer a byte-oriented
  Crystal record, or move it to a dedicated legacy import/export boundary.

Compatibility implications
--------------------------
- Existing Crystal IDs 0-255 remain representable. Native content tables and
  bag state can hold wider IDs, but unconverted live Pokemon/battle/WRAM paths
  deliberately reject IDs above 255 rather than truncate them.
- Native item ID 255 cannot round-trip through the Crystal save format because
  Crystal uses `0xff` as its list terminator. The native terminator is `0xffff`,
  and serialization maps it explicitly to/from the legacy terminator.
- No intro visuals, assets, flow, title behavior, options behavior, music
  behavior, RTC behavior, renderer, audio subsystem, or network protocol was
  changed.

Save-format implications
------------------------
- The on-disk format remains Crystal-compatible and byte-sized; no save version
  or native save schema was introduced.
- Native IDs are range-checked during legacy serialization. An expanded value
  that cannot be represented aborts serialization instead of corrupting a save.
- Loading widens representable legacy bytes into native IDs. Legacy item-list
  byte `0xff` maps to native `ITEM_LIST_END` (`0xffff`).
